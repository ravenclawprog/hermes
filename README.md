# HERMES

**Hermes** — это отказоустойчивая микросервисная платформа для совместной работы с удаленными документами в реальном времени, управляемая через интерактивный CLI-интерфейс. 
Проект проектируется с упором на распределенную архитектуру, асинхронный стриминг событий и готовность к горизонтальному масштабированию в облачной инфраструктуре.

## 🚀 Основной функционал

* **Управление документами (CLI)**: Создание, чтение, удаление и атомарное дополнение документов на удаленном сервере. 
* **Интерактивное редактирование**: Бесшовная интеграция консоли с системными редакторами (по типу `nano` / `vim`) для изменения текста (как, например, реализовано в `git`)
* **Real-time нотификации**: Быстрая доставка уведомлений по протоколу WebSocket (создание/изменение документов)
* **Оптимистическая блокировка**: Защита от конфилктов при одновременном редактировании одного документа несколькими пользователями

## 🛠 Технологический стек и архитектура

*   **Язык разработки:** Go (Golang) — высокая конкурентность (горутины, каналы) на клиенте и сервере.
*   **Брокер сообщений:** Apache Kafka — асинхронный транспорт для событий совместной работы, обеспечивающий слабую связность микросервисов.
*   **Реляционная БД:** PostgreSQL — строгое ACID-хранилище данных, реализующее паттерн *Transactional Outbox* для гарантированной доставки событий.
*   **In-memory БД:** Redis — маршрутизация WebSocket-сообщений между независимыми подами через *Redis Pub/Sub* и кэширование статусов пользователей.
*   **Оркестрация:** Kubernetes — контейнеризация (Docker) и деплой сервисов с поддержкой авто-масштабирования (HPA).

## 🎯 Уточнение требований

**Hermes** — это аналог Notion с консольным интерфейсом: пользователи организуют базу знаний в рабочих пространствах, редактируют документы привычным редактором и получают уведомления об изменениях.

README описывает **целевые возможности проекта**. Сейчас реализован начальный CLI на Go: каркас команд и запуск системного редактора; серверные операции заменены заглушками. Сначала прорабатываются требования и пользовательские сценарии, затем приложения. Правила ниже — исходная модель для дальнейшего обсуждения.

* **Два режима интерфейса:** Отдельные команды для разовых действий и постоянно открытый терминальный интерфейс (TUI) для работы с пространствами, документами и входящими.
* **Рабочие пространства:** Общие пространства для команд и личное пространство каждого пользователя. Все документы принадлежат пространствам.
* **Сохраняемые входящие:** Приоритет первой версии — уведомления, доступные даже после завершения клиента. Упомянутая выше доставка через WebSocket остаётся целевой возможностью следующего этапа; сначала TUI обновляет входящие периодическими запросами.
* **Разделение событий и уведомлений:** Внутренние события отражают изменения системы, а пользовательские уведомления создаются только для событий, требующих внимания адресата.

## 🖥 Способы работы

* `hermes` без аргументов открывает постоянно работающий терминальный интерфейс (TUI): пространства, документы, поиск и входящие. Собственный командный интерпретатор не требуется.
* Отдельные команды (`hermes workspace list`, `hermes doc read/edit`, `hermes inbox list`) выполняют действие и завершают процесс. Чтение документа должно поддерживать вывод чистого содержимого для пайплайнов.
* Оба режима используют одну учётную запись, API, права доступа и серверное состояние входящих. Выбор текущего пространства хранится локально; явный параметр пространства имеет приоритет. Сам выбор пространства не предоставляет доступ.
* Редактирование текста выполняется во внешнем редакторе. Пока он занимает терминал, входящие накапливаются; после возврата TUI обновляет их. При ошибке сохранения или конфликте локальные правки сохраняются для восстановления.
* Отдельный `hermes stream` можно добавить позднее как способ наблюдать за входящими; он не нужен для их сохранения.

## 🧩 Предметная модель

Все идентификаторы стабильны и не зависят от изменяемых имён. Даты задаются сервером в UTC. Для изменяемых сущностей используется `version`: обновление с устаревшей версией возвращает конфликт без частичного изменения данных.

### Пользователь

Атрибуты: `id`, уникальный без учёта регистра `username`, `display_name`, уникальный без учёта регистра `email`, `status` (`active`, `deleted`), `created_at`, `updated_at`, `deleted_at`, `version`.

Учётные данные и сессии хранятся отдельно от публичного профиля; email виден только владельцу. Способ аутентификации предстоит выбрать: одного имени пользователя недостаточно для входа. Смена email требует подтверждения нового адреса; до подтверждения действует старый адрес.

* Регистрация атомарно создаёт пользователя, его личное пространство и членство владельца.
* Пользователь просматривает и изменяет свой профиль. Другим участникам доступен только публичный профиль.
* Удаление учётной записи требует повторного подтверждения личности. Оно блокируется, пока пользователь владеет общими пространствами: сначала нужно передать владение или удалить эти пространства.
* При удалении отзываются сессии, удаляются членства, личное пространство и его документы становятся недоступны. В общих документах сохраняются авторство и история с отметкой «удалённый пользователь»; входящие удалённого пользователя больше не обслуживаются. Сроки физического удаления и обезличивания данных нужно определить отдельно.

### Рабочее пространство

Единая сущность для личных и общих документов. Каждый документ принадлежит ровно одному пространству; отдельного `owner_user_id` у документа нет.

Атрибуты: `id`, `name`, `description`, `kind` (`personal`, `shared`), `owner_id`, `created_at`, `updated_at`, `deleted_at`, `version`.

Членство: `workspace_id`, `user_id`, `role` (`owner`, `admin`, `editor`, `viewer`), `joined_at`. Пара пользователя и пространства уникальна; у активного пространства ровно один владелец, совпадающий с `owner_id`.

* `viewer` читает документы; `editor` дополнительно создаёт, редактирует и удаляет документы. `admin` также меняет настройки пространства и управляет участниками с ролями `editor`/`viewer`.
* Владелец обладает правами администратора, назначает администраторов, передаёт владение и удаляет общее пространство. Менять или исключать владельца обычной операцией управления участниками нельзя.
* Личное пространство создаётся автоматически, доступно только владельцу, не поддерживает приглашения и передачу владения. Его нельзя отдельно удалить; имя и описание можно изменить.
* Приглашение в общее пространство адресуется существующему активному пользователю. Атрибуты: `id`, `workspace_id`, `inviter_id`, `invitee_id`, `role`, `status` (`pending`, `accepted`, `declined`, `revoked`, `expired`), `expires_at`, `created_at`. Принятие действительно только для адресата и повторно проверяет актуальность приглашения и пространства.
* Удаление общего пространства после явного подтверждения атомарно закрывает доступ к документам, членствам и приглашениям. Это логическое удаление; восстановление пока вне первой версии.

### Документ

Документ первой версии — Markdown-страница. Блочная модель Notion, вложенность страниц и перенос между пространствами остаются открытыми вопросами.

Атрибуты документа: `id`, `workspace_id` (не меняется в первой версии), `title`, `content`, `format` (`markdown`), `version`, `created_by`, `updated_by`, `created_at`, `updated_at`, `deleted_at`. Названия могут совпадать; для точного обращения используется ID.

* Документы видны участникам своего пространства с учётом роли. Публичные ссылки и индивидуальные права на отдельные документы пока не входят в модель.
* Список и поиск ограничены доступными пространствами и поддерживают постраничную выдачу.
* Создание требует непустого заголовка. Сохранение заголовка и текста атомарно увеличивает версию; неизменённое содержимое не создаёт событие обновления.
* При конфликте клиент сохраняет локальные правки и предлагает получить актуальную версию для ручного сравнения. Автоматическое слияние и одновременное редактирование текста пока не предусмотрены.
* Удаление логическое, с проверкой версии и подтверждением; документ становится недоступен. Восстановление и пользовательская история версий пока не входят в первую версию.
* Подписка на изменения документа: `user_id`, `document_id`, `created_at`. Подписываться и отписываться может любой читатель; при потере доступа подписка удаляется.

## 🔔 Внутренние события и уведомления

**Внутреннее событие** фиксирует состоявшееся изменение предметной модели. Чтение, поиск, неуспешная команда и конфликт события изменения не создают. **Уведомление** — отдельная запись для конкретного получателя, которой может потребоваться его внимание. Не каждое событие порождает уведомление.

Конверт события: `event_id`, `type`, `schema_version`, `occurred_at`, `actor_id`, `aggregate_type`, `aggregate_id`, `aggregate_version`, `workspace_id` (если применимо), `correlation_id`, `payload`. Событие содержит необходимые для обработки идентификаторы и изменения, без секретов и полного текста документов.

| Группа | Внутренние события | Уведомления и адресаты |
| --- | --- | --- |
| Пользователи | `UserCreated`, `UserUpdated`, `UserDeleted` | `ProfileChanged` — владельцу при изменении username/email. Регистрация и удаление не рассылаются другим пользователям. Событие смены email возникает после подтверждения. |
| Пространства | `WorkspaceCreated`, `WorkspaceUpdated`, `WorkspaceDeleted`, `WorkspaceInvitationCreated/Accepted/Declined/Revoked/Expired`, `WorkspaceMemberAdded`, `WorkspaceMemberRoleChanged`, `WorkspaceMemberRemoved`, `WorkspaceOwnershipTransferred` | Приглашение — адресату; принятие/отклонение — пригласившему; изменение роли/исключение — затронутому участнику; передача владения — прежнему и новому владельцу; удаление — прежним участникам. Создание, переименование и истечение приглашения не создают отдельного уведомления. |
| Документы | `DocumentCreated`, `DocumentUpdated`, `DocumentDeleted`, `DocumentSubscriptionCreated/Deleted` | Изменение/удаление — подписчикам. Создание документа и подписка сами по себе не уведомляют. |

Уведомление: `id`, `recipient_id`, `category` (`users`, `workspaces`, `documents`), `type`, `source_event_id`, `actor_id`, `workspace_id`, `target_type`, `target_id`, `created_at`, `read_at`. Все активные пользователи имеют собственные входящие, включая пользователей только с личным пространством.

* Входящие хранятся на сервере независимо от запущенного клиента. Поддерживаются список с фильтром категории/непрочитанного и пагинацией, счётчик, переход к объекту, отметка одного или всех уведомлений прочитанными. Для «прочитать все» фиксируется граница списка, чтобы не отметить новые поступления.
* Получать и менять входящие может только их адресат. Открытие объекта повторно проверяет текущие права; уведомление не предоставляет доступ.
* Исключение из пространства и его удаление могут уведомить бывшего участника, но запись содержит только минимальный факт без текста документов. Прежние уведомления о недоступных документах скрываются, в том числе из счётчика; переход по старой ссылке возвращает недоступность.
* На первом этапе настройки `enabled` задаются пользователем для каждой из трёх категорий (по умолчанию включены). Отключение влияет на создание будущих уведомлений, не удаляет старые и не отменяет внутренние события. Приглашения доступны в списке приглашений даже при отключённой категории.
* Изменение собственного профиля — исключение из правила подавления уведомлений о собственных действиях. Остальные собственные действия не уведомляют автора. Одно событие создаёт не более одного уведомления для каждого адресата.
* Повторная обработка одного события не создаёт дубликаты: уникальность `(recipient_id, source_event_id)`. Объединение нескольких последовательных изменений страницы в одно уведомление можно добавить позднее.
* Долговечные входящие — приоритет первой версии. Открытый TUI периодически обновляет список и счётчик. Мгновенная доставка через WebSocket — последующая оптимизация; она не заменяет сохранение входящих.

## 🏗 Логическая архитектура

Границы ответственности: учётные записи и сессии; пространства, членства и приглашения; документы и подписки; события и входящие. Это логические модули, а не обязательное количество отдельных сервисов. Оба режима консольного клиента обращаются к одному API; выбор HTTP или gRPC ещё предстоит закрепить.

PostgreSQL хранит предметные данные, входящие и outbox. Изменение данных и запись внутренних событий выполняются **в одной транзакции**. Публикация и обработка событий допускают повторы; обработчик уведомлений идемпотентен. После успешного сохранения входящие могут появиться с задержкой. Контроль доступа выполняется сервером при каждой операции и при выдаче входящих.

Для целевой распределённой реализации рассматриваются Kafka как транспорт событий, Redis для маршрутизации живой доставки и Kubernetes для развёртывания. Их наличие не является условием проверки пользовательских сценариев. Сбой живой доставки не должен приводить к потере сохранённых входящих. Outbox обеспечивает возможность повторной публикации; подтверждение обработки следует за сохранением результата.

[Логическая схема](arch/arch.puml). Сценарии представлены диаграммами последовательности; названия операций обозначают логический API, а не окончательный синтаксис команд или сетевой контракт.

## ❓ Вопросы для дальнейшей проработки

* Способ регистрации, подтверждения email, аутентификации и восстановления доступа.
* Нужны ли дерево страниц, вложенные пространства, перенос документов и отдельные права на страницы.
* Нужны ли восстановление удалённого, история версий и автоматическое слияние.
* Сроки хранения входящих, событий и удалённых данных, правила очистки и обезличивания.
* Лимиты размеров документов, частоты запросов и приглашений.
* Детальная раскладка TUI, окончательные команды и сетевые контракты.
