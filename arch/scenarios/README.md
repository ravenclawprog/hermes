# Сценарии Hermes

Сценарии описывают проектируемое поведение, а не уже реализованный сервер.
Структура document-service соответствует [схеме программы](../hermes-document-service.puml),
клиентские операции — [hermes-cli](../hermes-cli.puml) и
[редактированию с черновиками](../hermes-cli-editing.puml).

Контракты клиента разделены на [внутренние Go-интерфейсы](../contracts/internal/hermes-cli.md)
и [внешние запросы, ответы и WebSocket-сообщения](../contracts/external/hermes-cli.md).
Имена и поля внешних сообщений пока являются проектом для согласования.

| Файл | Содержание |
| --- | --- |
| [auth.puml](auth.puml) | Вход, локальное сохранение токена, middleware, Redis-сессии, WebSocket handshake и logout |
| [users.puml](users.puml) | Регистрация, профили, подтверждение email и границы удаления аккаунта |
| [workspaces.puml](workspaces.puml) | Пространства, членства, приглашения, роли, передача владения и удаление |
| [documents.puml](documents.puml) | Чтение, поиск, редактирование через DraftStore, конфликты, подписки и удаление |
| [events_dispatch.puml](events_dispatch.puml) | Предметная транзакция, альтернативы публикации, маршрутизация и live/offline-доставка |
| [notifications_inbox.puml](notifications_inbox.puml) | Подключение, накопленные сообщения, открытие объекта и предложенное распространение настроек |

## Границы слоёв

Клиентская presentation вызывает `internal/app`; сетевые запросы выполняет выбранный
HTTP/gRPC-адаптер. Live-клиент имеет отдельный streaming-контракт: его устройство ещё
нужно детализировать, это не существующий InboxRemote.

В document-service API проверяет DTO и через middleware вызывает Auth.ValidateSession.
Auth использует Redis SessionStore; только подтверждённая сессия позволяет передать
идентичность в прикладную операцию. Отсутствие сессии и недоступность Redis — разные
ошибки. Для краткости повторные проверки обозначены `ref` или общей заметкой.

Прикладной слой получает актуальные данные через репозитории, применяет предметные
политики и использует UnitOfWork для транзакционных изменений. Участник `internal/domain`
обозначает применение правил к загруженному состоянию, а не отдельный процесс.
Сетевые ответы и клиентские операции, не существенные для данного сценария, сокращены.

## Статусы и открытые границы

Приоритет имеют [ADR](../decisions/README.md) и принятое направление из
[требований](../requirements.md). `OPEN`, `PROPOSED`, `opt` и `ref` обозначают
невыбранные протоколы; они не превращают предложение в гарантию.

- Активные сессии находятся в Redis; HNS проверяет их напрямую (ADR-001).
- PostgreSQL и Redis не имеют общей транзакции. Удаление аккаунта, отзыв сессий и
  гонка с новым входом требуют согласованного протокола; сценарии не выдают его за готовый.
- Kafka — принятый канал. Outbox/CDC и прямая отправка после commit показаны как
  альтернативы; события относятся только к состоявшимся изменениям (ADR-002).
- Онлайн-доставка идёт во все активные подключения. По текущим заметкам сообщения
  офлайн-пользователя сохраняются и выдаются одной подключившейся сессии.
  Классы сообщений, координация экземпляров HNS, гонки, ack, повторы и очистка открыты.
  Не предполагается обязательная запись каждого live-сообщения перед отправкой.
- Авторизация получателей и свежесть данных для маршрутизации открыты. HNS не читает
  предметный PostgreSQL напрямую; внутренний API прав не объявляется принятым.
- Распространение настроек через PostgreSQL → Redis → Pub/Sub предложено в ADR-003.
  Применение ко всем подключениям обязательно; частичные сбои и задержка требуют решения.
- Постоянная история входящих, счётчики и read-state отделены от восстановления
  офлайн-сообщений; их контракт не закреплён этими схемами.

## Проверка

Каждый `.puml` — самостоятельная sequence-диаграмма без внешних include.
Проверять нужно не только синтаксис, но и полный рендер всех шести файлов в PlantUML.
